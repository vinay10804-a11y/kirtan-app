# Sacinandana Swami and Gour Krishna Kirtans

Offline-capable web app (PWA) for kirtans, bhajans and guided japa, built for Vinay
(devotee name Vinoda Govinda; use that name when talking about this project).
Hosted on his Cloudflare account: a Worker serves `site/` and streams audio from the
R2 bucket `kirtans` at `/stream/*`.

## Layout
- `site/`: the app (plain HTML/CSS/JS, no framework). `app.js` renders hash routes into `#view`;
  `sw.js` caches the shell and serves saved audio offline; `catalog.json`, `videos.json` and
  `photos.json` are generated by the build.
- `worker/index.js`: serves `/stream/*` (and the older `/media/*`, `/audio/*`) from R2 with Range
  support, `/api/*` (accounts, `worker/api.js`) and `/k/<id>` share pages (`worker/share.js`);
  everything else is a static asset.
- `tools/`: `build.mjs` (scan → compress → catalog), `classify.mjs` (sorting rules),
  `upload.mjs` (to R2), `fetch-japa.sh` + `videos.mjs` (YouTube/SoundCloud japa),
  `fetch-spotify.sh`, `photos.mjs`, `pull-source.mjs` (originals from R2 → `source/`).
- `publish.sh`: the full pipeline on a Mac.

## What's online, and the owner's Mac (since 19 Oct 2026)
`site/catalog.json` (in git) is the record of what's online. The build keeps every catalog entry even
when its original isn't on the Mac, re-applies `classify.mjs` to it (each entry stores `rel`, its path
in the Kirtans folder), and only compresses files that are new. So the owner may delete originals and
`build/` once published, and the Kirtans folder only needs new recordings until they're published.
`--forget-missing` (build or publish) drops entries whose original is gone; use it only when the owner
wants recordings removed. Cover art lives in `site/covers/` (in git).

Sorting/place changes with no recordings to hand: `node tools/build.mjs none && npx wrangler deploy`.

Audio format (owner's choice, 19 Oct 2026): AAC 96 kbps stereo in .m4a, made with Apple's encoder
(`aac_at`). Since 22 Oct every recording is also levelled to -16 LUFS (the originals differed by
34 dB, so a playlist jumped between barely audible and very loud): FORMAT `aac96lv` in build.mjs, files
under `stream/` in the `kirtans` bucket. `levelling()` uses a plain volume change, or volume plus a
peak limiter for gains up to 8 dB, and loudnorm only for very quiet recordings (it's slow). Total about
3.5 GB, inside R2's free 10 GB; keep it there. The older copies under `media/` (aac96) and `audio/`
(MP3) are no longer used and can be removed with an R2 lifecycle rule. The owner chose not to keep a backup of the originals on
Cloudflare: the published files are the only copy once local files are deleted, so a future format
change can only re-encode files whose originals are on the Mac (others are kept as they are).

## Working in the cloud (no Mac)
There are no originals in the cloud (the `kirtans-source` backup was removed at the owner's request;
`tools/pull-source.mjs` only matters if it's ever recreated). Sorting changes need no recordings.
With `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` set, Wrangler deploys and uploads non-interactively.

For sorting changes, or new recordings in a folder of their own:
```
npm install
node tools/build.mjs <folder with only the new recordings, or "none">   # prints the category summary
node tools/upload.mjs                 # new compressed audio → R2 bucket "kirtans"
npx wrangler deploy
```
Show the owner the category summary before deploying. YouTube downloads often fail from cloud IPs;
if `tools/fetch-japa.sh` is blocked, give the owner the Mac commands instead.

## Offline start (fixed 22 Oct 2026)
The app must open with no signal (e.g. on the Underground). `sw.js` opens pages network-first with a
3-second timeout, falling back to the cached `./`; never cache or serve `index.html` (Cloudflare
redirects it to `/`, and Safari refuses redirected responses for page loads, which stopped the app
opening offline). Data JSON falls back to cache after 4 seconds. EB Garamond is self-hosted in
`site/fonts/` (OFL) and pre-cached, so nothing render-blocking comes from another site. On iPhone the
home-screen app has its own storage, separate from Safari: kirtans must be saved from inside it.
JS, CSS, the manifest and data JSON are network-first (4 s) too: serving stored copies first mixed an old
app.js/styles.css with a new index.html after a deploy. Cover pictures of saved kirtans, and of whatever
is played, are kept in the `kirtan-art` cache (`keepArt` in app.js); a picture that can't load falls back
to the initials tile.

## Accounts (22 Oct 2026, owner chose email + password)
Signing in keeps a person's favourites and playlists on all their devices; without an account the app
works as before (device only). Server: `worker/api.js` at `/api/*` with the D1 database
`kirtan-accounts` (binding `DB`, tables in `migrations/`; apply with
`wrangler d1 migrations apply kirtan-accounts --remote`). Passwords never leave the device: app.js
derives a key (PBKDF2-SHA256, 600,000 rounds, salt `kirtan-app|<email>`) and the server stores
SHA-256(random salt + key), which keeps the Worker inside the free plan's CPU limit. Sessions are
HttpOnly Secure SameSite=Lax cookies (1 year); 10 wrong passwords lock an email for 15 minutes;
requests from other origins are refused. `site/library.js` (shared by app and server) merges libraries
item by item, latest change wins, with tombstones for deleted playlists. Sync replies are merged with
changes made while they were in flight, and playlists are updated in place (code may hold one across
an `await`). Sign-out clears the account's data from the device. No email can be sent (free plan), so
forgotten passwords go through the owner: `node tools/account.mjs reset <email>` prints a temporary
password; `count` shows how many accounts exist. Don't create test accounts on the live site; test
with `wrangler dev --local` (localhost and 127.0.0.1 act as two devices).

## Playback, as smooth as SoundCloud and Spotify (platform audit, 22 Oct 2026)
- Quick skips: `load()` counts calls (`loadSeq`); only the latest tapped kirtan starts.
- A dropped connection retries (`recovery`, `resumeAfterDrop`) from the same second, waiting for
  `online` when offline. Offline, next/previous skip kirtans that aren't saved (`stepIndex`).
- Repeat cycles off → all → one. A spinner shows while buffering. The queue is stored, so it
  survives closing the app. The phone's back button closes the player (history entry).
- Share links are `/k/<id>`: the Worker adds Open Graph tags (title, artist, picture) so WhatsApp and
  Messages show a preview; app.js turns the address into `#/play/<id>`.
- Signed-in people continue listening on any device: positions and the last kirtan sync with the
  account (`positions`, `last` in library.js; later change wins).
- Library shows recent searches and how much space saved kirtans use.
- Owner's requests, 24 Oct 2026: the kirtan that's playing (or paused) stands out in every list (tinted
  band, teal title, moving bars in place of its number); the lock screen and Control Centre show
  previous/next kirtan buttons (no 15/30-second skip handlers in mediaSession: iPhones show those
  instead of next/previous); the player's "Play next" button opens "When this kirtan ends": Play the
  next kirtan, Loop this kirtan, Play once then stop, Loop the whole list (`REPEAT` in app.js; also in
  the ⋯ menu of the kirtan that's playing).
